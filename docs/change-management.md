# 变更管理

## 变更状态机

每个变更通过 `change.md` 中的 `status` 字段驱动流转。状态机如下：

```
                        ┌──────────────────────────────────────┐
                        │                                      │
                        ▼                                      │
   drafting ──▶ reviewing ──▶ approved ──▶ coding ──▶ testing ──┤
                                                               │
                    ┌──────────────────────────────────────────┘
                    ▼
              reviewing ◀── ci ◀── verifying ◀── done
```

| 状态 | 说明 | 所属阶段 |
|------|------|---------|
| `drafting` | 规格编写中 | ① 需求分析 |
| `reviewing` | 规格评审中 | ① 需求分析 |
| `approved` | 规格已确认，可以开始编码 | ① → ② 交接 |
| `coding` | 编码实现中 | ② 编码实现 |
| `testing` | 测试编写中 | ③ 单元测试 |
| `reviewing` | 代码评审中 | ④ 专家评审 |
| `ci` | CI 门禁执行中 | ⑤ CI 门禁 |
| `verifying` | 部署验证中 | ⑥ 部署验证 |
| `done` | 变更完成，已交付 | 交付 |

## 变更文档模板

每个变更对应 `.harness/changes/<id>/` 下的三个文件：

### change.md — 变更卡

变更卡是**规格的真相源**，包含：

```
- 变更标题
- 变更描述
- 状态（drafting / reviewing / ...）
- AC（验收条件，可测试）
- 边界情况（≥3 个）
- 设计约束
- 测试策略
- 技术备忘录
```

### review.md — 评审报告

由 `expert-reviewer` 技能生成，包含：

```
- 功能完整性（对照 change.md）
- 架构合规性
- 编码规范
- 代码质量
- 安全性
- 测试质量
- 流程合规
- SDD/TDD 合规
- 问题列表（🔴 严重 / 🟡 建议）
```

### verify.md — 部署验证报告

由 `deploy-verify` 技能生成，包含：

```
- 健康检查结果
- 冒烟测试结果
- 关键链路验证结果
- 降级链路验证结果
- 回滚预案
```

## 为什么要用变更管理？

| 问题 | 变更管理的解法 |
|------|---------------|
| 变更不可追溯 | 每个变更都有完整生命周期记录 |
| 需求经常变，不知道改了什么 | change.md 记录每次变更的 AC 和边界 |
| 评审没有依据 | review.md 逐项对照 change.md 检查 |
| 上线后出问题不知道是否该回滚 | verify.md 记录验证结果和回滚预案 |
| 多轮对话上下文丢失 | 变更卡 + 交接文档可以续接工作 |
