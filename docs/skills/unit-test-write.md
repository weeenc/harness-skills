# ③ 单元测试编写 — unit-test-write

> **流水线阶段**: ③ 第三步
> **技能标识**: `unit-test-write`
> **输入**: ② 阶段的实现代码 + change.md
> **出口门禁**: 测试通过、核心逻辑覆盖率 ≥80%、覆盖全部 AC 与边界

## 它做什么？

为实现代码编写完整的单元测试套件，确保：

- 每条 AC 至少有一个测试
- 每条边界情况有一个专门测试
- 每条降级路径有一个专门测试
- 核心逻辑覆盖率 ≥80%

## 什么时候用？

- 实现代码已完成，需要完善测试
- 流水线第三步，在编码实现之后

## 工作流程

### Step 1: 梳理测试矩阵

从 `change.md` 提取所有 AC 与边界情况，建立"测试点 → 测试用例"映射表，确保无遗漏。

### Step 2: 编码前让失败测试先存在

在写实现代码之前，先写测试——这样测试是在"不知道实现"的情况下写的，更贴近行为，而不是实现。

### Step 3: 编码后补齐测试

实现完成后，补充边界、降级、回归测试：

| 测试类型 | 说明 | 必须？ |
|---------|------|--------|
| AC 测试 | 验证每条验收条件 | ✅ 必须 |
| 边界测试 | 验证边界情况 | ✅ 必须 |
| 降级测试 | 验证错误路径 | ✅ 必须 |
| 异常测试 | 验证异常处理 | ✅ 推荐 |
| 回归测试 | 验证不破坏已有功能 | ✅ 推荐 |

### Step 4: 覆盖率检查

运行覆盖率工具，确认核心逻辑覆盖率 ≥80%。

## 核心原则

> **每条 AC 至少一个测试，每条降级路径一个专门测试，核心覆盖率 ≥80%。禁止只测 happy path。**

## 出口门禁

- [ ] 全部测试通过
- [ ] 核心逻辑覆盖率 ≥80%
- [ ] 覆盖全部 AC
- [ ] 覆盖全部边界情况
- [ ] 覆盖全部降级路径
