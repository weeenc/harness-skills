# ④ 专家评审 — expert-reviewer

> **流水线阶段**: ④ 第四步
> **技能标识**: `expert-reviewer`
> **输入**: 代码 + 单元测试
> **产出**: 目标 `report.md` 的④章节（legacy: review.md）
> **出口门禁**: 0 个 🔴 严重问题

## 它做什么？

多维度代码审查，区分严重问题与建议改进，确保代码质量达到交付标准。

### 审查维度

| 维度 | 检查内容 |
|------|---------|
| 功能完整性 | 对照 change.md 检查是否实现所有 AC |
| 架构合规 | 是否符合工程结构规范、分层架构 |
| 编码规范 | 是否符合编码规范、命名规范、代码风格 |
| 代码质量 | 圈复杂度、重复代码、魔法数字、过长方法 |
| 安全性 | SQL 注入、XSS、敏感信息泄露、权限校验 |
| 测试质量 | 测试覆盖率、测试是否测行为而非实现 |
| 流程合规 | 是否跳步、change.md 是否完整 |
| SDD/TDD 合规 | 是否先写失败测试、是否垂直切片 |

### 问题分级

| 级别 | 标记 | 含义 | 是否放行 |
|------|------|------|---------|
| 严重 | 🔴 | 功能缺失、安全漏洞、架构违规 | ❌ 必须修复 |
| 建议 | 🟡 | 可优化但不阻塞 | 可选 |

## 什么时候用？

- 编码和测试都已完成，需要质量把关
- 流水线第四步，在单元测试编写之后

## 核心原则

> **不手下留情。逐项审查，0 个 🔴 才放行。**

## 审查架构 — 双轴并行子智能体

expert-reviewer 采用**双轴并行子智能体**架构，两轴各由独立子智能体运行、互不可见对方推理，防止一个轴掩盖另一个轴：

- **Spec 轴子智能体**：对照 `change.md` 检查代码是否实现了该做的（缺失 / 未完整实现的 AC），且没做不该做的（越界行为、实现看似覆盖但写法错误的需求）。每条发现引用 change.md 对应行号。
- **Standards 轴子智能体**：对照 `.harness/rules/` 与代码质量基线检查合规性（已文档化规范的硬违规 + 代码味道判断项）。每条发现引用「规范文件 + 条款」或对应 hunk。

**派发与保障**：
- 宿主提供 subagent 原语（Reasonix `parallel_tasks` / Claude Code Task tool / Codex Agent）时，**必须**一次并行派发两个只读子任务，禁止串行或合并为单任务。
- 聚合时**不合并、不排序**，报告分 `## Spec 轴报告` / `## Standards 轴报告` 两节原样呈现。
- 宿主无 subagent 原语时降级为同一 agent 顺序两遍评审，且必须在 report 中标注「降级模式」，不得伪装双轴独立。
- 完成标志处跑 `harness-gate.sh review-check <id>`（review-check 门禁）机械校验双轴结构：Spec/Standards 节头、审查范围标注、🔴 条目引用，rc=0 方可 `reviewing → ci`。

## 为什么需要专家评审？

| 问题 | 评审的解法 |
|------|-----------|
| AI 自己写的代码自己检查不出来问题 | 有专门的评审视角，不手下留情 |
| 测试覆盖了但代码质量差 | 评审关注代码质量，不只看测试 |
| 架构违规不易被测试发现 | 评审逐项检查架构合规 |
| 安全问题容易被忽略 | 评审有专门的安全检查维度 |
