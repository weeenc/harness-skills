# 规范库管理 — harness-standard

> **技能标识**: `harness-standard`
> **使用场景**: "改一条团队规范"——新增/修订/归档/索引，重大约束留人审批
> **定位**: `rules/` 是团队的"宪法"——流水线技能（coding-skill / expert-reviewer / unit-test-ci）都按它执行。规范一旦被 AI 随手改动，会造成评审标准漂移、门禁口径不一，因此**规范变更的流程比规范本身更重要**

## 它做什么？

管理 `.harness/rules/` 下的规范文件：**新增、修订、归档、索引**，并保证规范变更可追溯、重大约束调整必须人类审批。

## 什么时候用？

- 团队需要新增一条规范（新约束/新流程）
- 现有规范需要修订（措辞调整或重大约束变更）
- 规范已过期/被取代，需要归档但保留历史
- 需要重建规范索引，或查看某条规范当前状态

## 规范库结构

```
.harness/rules/
├── <规范名>.md          # 每条规范一个文件（如 编码规范.md / 开发流程规范.md）
└── README.md / INDEX    # 规范索引（列表 + 一句话职责）
```

## 四种操作

### `add <文件/内容>` — 新增
- 新建规范文件：命名规范（kebab-case）、frontmatter（`name` / `scope` / `version` / `updated`）
- 登记到索引
- **默认不直接生效**：新规范需评审确认后才被流水线引用

### `edit <规范名> <变更说明>` — 修订
- 先展示**改动 diff** 给人类
- 按严重度分类：
  - **重大约束**（门禁标准、强制规则、禁止项）→ **必须人类审批**后才写入
  - **轻微调整**（措辞、示例、非强制建议）→ 可记录待批，仍建议过审
- 修订后 bump `version`、更新 `updated`

### `archive <规范名>` — 归档
- 把过期/被取代的规范移入 `archive/`（**不删除**，保留历史追溯）
- 索引中标注 `(archived)`

### `index` — 索引
- 重建/展示规范索引：规范名、版本、scope、状态（active/archived）、最后修订人/日期

## 审批纪律

- **重大约束**变更，AI **只能提交提案，不能自行定案**：

  ```
  提案: 修改 <规范> 的 <条目>
  现状: <原文>
  拟改为: <新文>
  理由: <影响哪些技能/门禁，为什么改>
  影响面: <哪些现有 change/代码可能受影响>
  ```

  人类批准后才写入规范文件。
- 每次修订在规范文件底部追加**变更记录**（`## 修订记录`：日期 / 变更摘要 / 审批人）
- 涉及技术架构约束时，与 `domain-modeling` 维护的领域模型/架构决策保持一致

## 为什么需要它？

| 问题 | 解法 |
|------|------|
| AI 随手改规范，评审标准漂移 | 重大约束变更必须人类审批 |
| 规范改了什么没有记录 | 修订记录（日期/摘要/审批人）强制追加 |
| 规范越积越多找不着 | `index` 索引 + active/archived 状态 |
| 规范改了评审口径没跟上 | 修订后提示跑 `/expert-reviewer` 复核 |

**重要**：规范修订后，提示跑一次 `/expert-reviewer`（或至少提示人类复核），确认现有代码/新代码仍符合新规范——避免"规范改了，评审口径没跟上"。

## 与流水线的关系

| 场景 | 归属 |
|------|------|
| 规范生命周期管理 | **本技能**（`/harness-standard`） |
| 规范执行（按规则编码） | `/coding-skill` |
| 规范合规评审（双轴 Standards 轴） | `/expert-reviewer` |
| 架构约束进规范 | `domain-modeling` / 架构决策记录 |

## 完成标志

- 规范文件已按类型操作完成（add/edit/archive），索引已同步
- 重大约束变更已获人类审批，修订记录已追加
- 已提示规范变更对评审口径的影响复核
