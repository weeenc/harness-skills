# 数据库设计 — harness-db-design

> **技能标识**: `harness-db-design`
> **使用场景**: 新增/改动数据模型时——从需求卡产出表结构、索引、约束与迁移设计
> **定位**: 与 `database-migration-toolkit` 分工——本技能负责**设计**（表结构长什么样），toolkit 负责**执行**（把设计落地为可回滚的迁移脚本）

## 它做什么？

从 `.harness/changes/<id>/change.md` 的需求与验收标准，产出**数据模型设计**：实体 → 表结构 → 索引 → 约束 → 迁移脚本，并把设计沉淀到 `.harness/wiki/数据模型.md` 与迁移文件。

## 什么时候用？

- change 新增/修改业务实体、关联关系、状态流转、字段
- 涉及索引、唯一约束、外键、级联策略
- 需要评估存量表迁移（加字段/改类型/拆表/归档）

## 核心机制

### 执行流程

```
Step 1: 识别实体（从 AC 与用户故事提取名词，确定关系与基数）
    ↓
Step 2: 表结构设计（字段 / 类型 / 约束 / 默认值）
    ↓
Step 3: 变更评估（对存量表：兼容性清单 + 迁移策略）
    ↓
Step 4: 落盘（更新 数据模型.md + 生成迁移脚本 + 补充 change.md 契约影响）
```

### 设计要点

- **主键**：优先自增/雪花/UUID（按项目约定），禁止用业务字段做主键
- **索引**：查询条件列加索引；组合索引遵循最左前缀；禁止无索引的全表扫（除非表极小）
- **约束**：业务不变式用 CHECK/UNIQUE 表达；外键按项目约定（如 MyBatis-Plus/JPA 生态常约定逻辑外键 + 应用层校验）
- **软删除**：如项目约定 `deleted` 字段，全表统一
- **时间字段**：`created_at` / `updated_at` 统一命名与默认值

### 存量表变更评估

| 存量表 | 变更类型（加字段/改类型/拆表/归档） | 是否破坏性 | 迁移策略 |
|--------|----------------------------------|-----------|---------|
| <表> | <变更> | 🟢 兼容 / 🔴 破坏 | <先加字段后回填 / 新表+切换+删旧> |

> **铁律**：破坏性变更（删列/改类型/改约束）必须先评审、可回滚、避开高峰，禁止直接 `DROP`。

### 目标产物

1. `.harness/wiki/数据模型.md`：实体关系图（Mermaid erDiagram）+ 表结构 + 变更记录
2. 迁移脚本：命名含版本号与变更 ID（如 `V<c>__C-0NN_<desc>.sql`），含 `up` 与 `down`（回滚）
3. change.md 的「契约影响 · 数据模型」补充本次模型变更摘要

## 为什么需要它？

| 问题 | 解法 |
|------|------|
| 表结构凭感觉设计，上线才发现缺索引 | 设计要点 + 自检清单 |
| 破坏性 DROP 导致数据丢失 | 破坏性变更先评审、可回滚、避开高峰 |
| 只写了 up 没有 down | 迁移脚本强制含回滚 |
| 文档和代码脱节 | `数据模型.md` 同步更新，禁止"代码改完了文档还是旧的" |

## 自检清单

- [ ] 每个实体有明确主键，索引覆盖查询路径
- [ ] 无破坏性变更未标注/未评审
- [ ] 迁移脚本含回滚（down）
- [ ] `数据模型.md` 已同步，无"代码改完了文档还是旧的"

## 完成标志

- 表结构/索引/约束已设计并自检通过
- `数据模型.md` 已更新（含 erDiagram 与变更记录）
- 迁移脚本已生成（含回滚），或已交 `database-migration-toolkit` 落地
