# 端到端测试 — harness-e2e

> **技能标识**: `harness-e2e`
> **使用场景**: "整条业务流真的走通了吗？"——验证跨模块/跨服务主链路
> **定位**: 与 `unit-test-write`（单测）互补：单测验证"模块内正确"，E2E 验证"跨模块/跨服务串起来正确"

## 它做什么？

基于 `.harness/changes/<id>/change.md` 的验收标准，生成或执行**端到端用例**——从用户入口出发，穿过真实接口/服务/存储，验证整条业务链路。`harness-quality` 的 flow→test 映射矩阵里，关键业务流的直接测试可由 E2E 承担。

## 什么时候用？

- change 的 AC 涉及跨模块/跨服务链路（如"下单 → 扣库存 → 发消息 → 出账单"）
- `harness-quality` 映射矩阵发现某条业务流无端到端覆盖
- 回归前验证核心主链路（冒烟级 E2E）

## 核心机制

### 执行流程

```
Step 1: 提取链路（从 AC + 影响面列出主链路与降级链路）
    ↓
Step 2: 生成用例（写 .harness/changes/<id>/e2e.md）
    ↓
Step 3: 执行（优先自动化，记录真实退出码与输出）
    ↓
Step 4: 结论（全 🟢 → verifying → done；有 🔴 → 如实退回）
```

### 用例卡格式

```markdown
## 用例 E2E-<n>: <链路名>
- 前置: <数据/服务状态准备>
- 步骤:
  1. <入口动作（接口/UI/消息）>
  2. <中间步骤>
- 期望终态:
  - <结果 1（响应/数据落库/消息发出）>
- 验证方式: <真实调用 / 自动化脚本>
```

### 铁律

- **真跑才算数**：E2E 用例必须真实执行并留证据，禁止"我看了一下应该没问题"替代
- **主链路必测**：每次 change 影响的主链路必须有 E2E 用例（或已有用例覆盖），不因"改动小"而跳过
- **失败如实报**：E2E 失败就是红灯，退回修复，不降低标准放行

## 为什么需要它？

| 问题 | 解法 |
|------|------|
| 单测全绿但串起来崩 | 跨模块/跨服务主链路 E2E 验证 |
| 降级链路（超时/依赖挂了）没人测 | 主链路 + 降级链路双路径用例 |
| 没有证据说"应该没问题" | 真实执行并记录退出码与输出 |

## 完成标志

- 用例卡已落盘 `.harness/changes/<id>/e2e.md`
- 用例已执行并留真实证据（退出码/输出），结果表已产出
- 主链路与降级链路均 🟢（或 🔴 已如实记录并退回）
