# Bug 诊断 — diagnosing-bugs

> **技能标识**: `diagnosing-bugs`
> **使用场景**: 当用户报告"这个出错/崩溃/性能慢"时

## 它做什么？

严谨的 Bug 诊断流程——先建立稳定复现的反馈循环，再分析根因。

## 核心原则

> **在建立稳定复现的反馈循环之前，禁止跳到"猜原因"阶段。**

## 工作流程

### Phase 1 — 建立反馈循环

这是整个技能的核心。如果你有一个能稳定复现 Bug 的**红/绿信号**——一个能明确捕捉到当前 Bug 的测试——你已经完成了 90% 的工作。

构建反馈循环的方式（按优先级排列）：

1. **失败测试** — 在能触达 Bug 的接缝处写单元/集成/E2E 测试
2. **Curl / HTTP 脚本** — 针对运行中的 dev server
3. **CLI 调用** — 带 fixture 输入，比对 stdout
4. **Playwright 无头浏览器脚本** — 驱动 UI，断言 DOM/console/network

### Phase 2 — 分析根因

有了稳定的反馈循环后，开始分析根因：
- 二分法缩小范围
- 检查日志和错误堆栈
- 分析输入数据

### Phase 3 — 修复

在测试保护下修复 Bug，确保修复后反馈循环通过。

## 什么时候用？

- 线上出 Bug，需要诊断
- 本地复现了异常，需要分析根因
- 性能问题，需要定位瓶颈

## 为什么需要它？

| 常见错误 | 正确做法 |
|---------|---------|
| 看到 Bug 直接猜原因 | 先建立反馈循环，再分析 |
| 反复修改反复试 | 有了反馈循环，一次改对 |
| 修了 Bug 但不知道是否真的修了 | 通过反馈循环验证 |
| 修了 Bug 但引入了新 Bug | 在测试保护下修复 |
