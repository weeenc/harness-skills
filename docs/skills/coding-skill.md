# ② 编码实现 — coding-skill

> **流水线阶段**: ② 第二步
> **技能标识**: `coding-skill`
> **输入**: 已审批的 `.harness/changes/<id>/change.md`
> **出口门禁**: 失败测试先存在且已转绿、编译通过、符合编码规范、逐 AC 通过 V1~V5 交叉验证 + D1~D10 全维度自查、独立复核（Step 4.7 子智能体）已过、机器门禁证据落盘、变更范围不越界

## 它做什么？

按已确认的需求卡与编码规范，采用 TDD 方式小步实现可编译的代码。

### 核心流程

```
change.md（已审批）
    ↓
Red：在接缝处写一个失败测试
    ↓
Green：最小实现通过测试
    ↓
Refactor：在测试保护下重构
    ↓
重复下一个垂直切片
```

## 什么时候用？

- 需求卡已审批，需要开始编码
- 流水线第二步，在需求分析之后

## 核心规则

### 先写失败测试

在编码之前，先在接缝处写一个反映需求的失败测试。这是 TDD 的核心——**测试描述的是行为，不是实现**。

### 垂直切片

一次只做一个 Red-Green-Refactor 循环。不要在同一个循环中处理多个行为。

### 最小实现

写刚好够让测试通过的最小代码。不要猜未来的需求，不要过度设计。

### 测试保护下重构

代码通过测试后，在测试保护下重构以改善设计。重构后所有测试仍然通过。

### 逐 AC 交叉验证（防"自写测试 + 实现错在同一处"）

每完成一个 AC，在标记"已闭环"前，**必须**逐条通过以下核对；任何一条不过，该 AC 视为未完成：

| # | 检查项 | 具体动作 |
|---|--------|---------|
| V1 | 字段/索引/键名对齐 | 写数据库索引、查询排序/过滤、update 字段前，用搜索工具核对模型/实体/schema 定义里的真实字段名；禁止照抄 change.md 里的字段名而不验证 |
| V2 | 符号/调用点全量核对 | 删除/改造一个函数、方法或符号后，全仓搜索（`grep`/`rg`/IDE 查找引用）该符号的所有引用，确认每一处都已处理，不只看影响面列出的文件 |
| V3 | 注释 vs 实现一致 | 写了"异步/不阻塞/惰性/有界/幂等"等意图注释的，逐条反查实现是否真如此 |
| V4 | 并发/异步语义自审 | 涉及并发、异步回调、共享可变状态时，先完成状态写入，再 close 通道 / 触发回调 / 解锁 / 提交 future，保证等待者读到完整一致的状态；临界区内操作一次性完成 |
| V5 | scope 自核 | 收尾时 `git diff HEAD --stat`（或等价）核对变更文件都在影响面内，出现范围外文件立刻停下拆分 |

### 全维度自查（镜像 expert-reviewer 十维度）

每完成一个 AC，除 V1~V5 交叉验证外，还必须对照以下十维度逐条自查。这不是"留给评审去查"，而是编码阶段就该守住的正确性底线；下表与 ④ expert-reviewer 的审查维度一一对应：编码先自查，评审只做独立复核。

| # | 维度 | 自查问题 |
|---|------|---------|
| D1 | 功能完整性 | 该 change 的每个 AC 都实现了吗？所有边界都处理了吗？有无 scope creep？实现符合设计约束吗？ |
| D2 | SDD 合规 | 实现是否严格对齐 change.md、未擅自扩 scope？（iterations）REQ/AC/TC 编号一致、无孤立 TC？ |
| D3 | 架构合规 | 模块间仅通过接口通信、依赖方向符合工程结构？新架构决策补了 ADR？ |
| D4 | 编码规范 | 命名/注释合规？无硬编码密钥/魔法值？外部调用有超时+重试+限频+降级？错误处理完整？ |
| D5 | 代码质量 | 函数/文件/圈复杂度在限内？无未使用/重复？日志级别合适？无明显代码味道？ |
| D6 | 安全 | 外部输入已校验？日志无敏感信息？无危险 DB/文件操作（需审批/受控）？无硬编码生产密钥？ |
| D7 | 测试质量 | 覆盖所有 AC 与边界？测了降级逻辑？核心覆盖率 ≥80%？Mock 合理？ |
| D8 | TDD 合规 | 核心业务逻辑测试先行？测试覆盖 AC/边界/降级路径？ |
| D9 | 流程合规 | 变更范围与 change.md 一致、无夹带？（V5 是此项的具象动作） |
| D10 | 领域语言一致 | 术语与 `.harness/CONTEXT.md` 一致？新领域概念已定义？ |

## 前置检查

1. `change.md` 存在且状态为 `approved`
2. 已加载 `.harness/rules/工程结构.md` + `编码规范.md`
3. 缺前置 → 退回 ① harnessing

## 为什么重要？

**编码实现是"把规格变成现实"的步骤。** 但它的核心不是"写代码快"，而是"在测试保护下小步前进"，确保每一步都是可验证的。

### 独立复核（Step 4.7，编码收尾前必做）

自查是"作者视角"，盲区共享——编码收尾、更新 `coding → testing` 前，必须由**不共享本次编码上下文**的独立子智能体（Reasonix `review`/`task`、Claude Code Task tool、Codex Agent）按 expert-reviewer 检查单重读 `git diff HEAD` + 新增文件，输出问题清单：fail-fast 前置（`git rev-parse` + 空 diff 拦截）→ 唯一一次捕获输入 → 派发独立复核（附文件:行号引用，≤400 词，禁止再派生 agent）→ 🔴 必修后复验 → 结论落 change.md。宿主无 subagent 原语时降级为另开新会话并标注；**主会话自审不算独立复核**。

## 出口门禁

只有同时满足以下 9 条，才允许把 `change.md` 状态从 `coding` 改为 `testing`：

- [ ] 失败测试已先行，且 build / lint / 核心测试全绿（含新增测试文件，V6 对完整工作区重跑）
- [ ] 逐 AC 完成 Step 4.5 精查，无未处理项
- [ ] `git diff HEAD --name-only` 的每个文件都在 change.md「影响面」内，影响面外变更已另行登记，影响面内承诺（wiki/ADR/配置/文档）逐项勾销
- [ ] 每个 AC / 边界 / 降级路径都有对应测试或明确"环境受限"标注，无"只改一半"的 AC
- [ ] 发现 spec 假设与代码不符时，已按「设计偏差」规则停下申报，而非照单全收
- [ ] 收尾完成 Step 4.6 全量自查（V1~V6 + D1~D10），逐条附实测证据，无未处理项
- [ ] **独立复核已过**：Step 4.7 由独立子智能体重读代码后 0🔴（或全部登记"记录在案未修"）；降级须标注，主会话自审不算
- [ ] 每个 AC 的闭环记录已留痕（影响面内调用点清单 + 核对结论写入 change.md），自查有证据、评审可追溯
- [ ] **机器门禁证据**：已跑 `.harness/scripts/harness-gate.sh check-style all <id>` 与 `static-analysis <id>`（退化直接执行亦可），经 `report.sh` 落盘 `gate-check-style.md` / `gate-static-analysis.md`；PASS 或显式 `[DEGRADED]`（须人工核对签名）——绝不静默跳过

> 全部 9 条满足 → **更新 `change.md` 状态 `coding → testing`**，进入 ③ 单测编写。
