# 6 阶段流水线

## 总览

```
                                   ┌──────────── 每一步都对照 .harness/rules/ 校验 ────────────┐
                                   │                                                          │
   人类意图                         ▼                                                          │
      │   ① harnessing  ──▶ ② coding-skill ──▶ ③ unit-test-write ──▶ ④ expert-reviewer ──▶ ⑤ unit-test-ci ──▶ ⑥ deploy-verify ──▶ 交付
      │   规格构建                 测试先行实现       测试完善              专家评审             CI 门禁            部署验证
      ▼
   .harness/changes/<id>/   （全程留档，状态机驱动）
```

新需求只保留变更卡与六阶段 report.md；全栈共享报告由协调者汇总。运行输出放 changes/.runtime/，规则与知识维护不变。

每个阶段对应 `.harness/skills/` 下的一个技能，**严格按序，不可跳步**。

## 阶段定义

### ① 需求分析 — `harnessing`

| 属性 | 说明 |
|------|------|
| **输入** | 一句话意图 |
| **产出** | 规格卡 + 验收标准 + 设计约束 + 测试策略 |
| **出口门禁** | 规格明确、AC 可测试、≥3 边界情况、测试策略清晰 |
| **核心原则** | 先搞清楚"做什么"，再想"怎么做" |

### ② 编码实现 — `coding-skill`

| 属性 | 说明 |
|------|------|
| **输入** | 已确认的规格卡 |
| **产出** | 失败测试 + 最小实现 |
| **出口门禁** | 失败测试先存在并转绿、构建/lint 通过、符合编码规范 |
| **核心原则** | 先写失败测试，再做最小实现，垂直切片 |

### ③ 单元测试编写 — `unit-test-write`

| 属性 | 说明 |
|------|------|
| **输入** | ② 阶段的实现代码 + change.md |
| **产出** | 完整测试套件 |
| **出口门禁** | 测试通过、核心逻辑覆盖率 ≥80%、覆盖全部 AC 与边界 |
| **核心原则** | 每条 AC 至少一个测试，每条降级路径一个专门测试 |

### ④ 专家评审 — `expert-reviewer`

| 属性 | 说明 |
|------|------|
| **输入** | 代码 + 单元测试 |
| **产出** | `report.md` ④章节（legacy: review.md） |
| **出口门禁** | 0 个 🔴 严重问题 |
| **核心原则** | 不手下留情，逐项审查，0 个 🔴 才放行 |

### ⑤ CI 门禁 — `unit-test-ci`

| 属性 | 说明 |
|------|------|
| **输入** | 通过 ④ 评审的完整变更 |
| **产出** | 门禁结果报告 |
| **出口门禁** | 所有 CI 阶段全绿 |
| **核心原则** | 机械化执行：编译 → 静态分析 → 架构约束 → 测试 → 安全扫描 |

### ⑥ 部署验证 — `deploy-verify`

| 属性 | 说明 |
|------|------|
| **输入** | 通过 ⑤ CI 的构建 |
| **产出** | `report.md` ⑥章节（legacy: verify.md） |
| **出口门禁** | 冒烟 + 健康检查通过、有回滚预案 |
| **核心原则** | "CI 绿"不等于"线上可用" |

## 辅助技能

除了 6 个流水线技能，还有 3 个辅助技能在需要时按需调用：

| 技能 | 调用时机 | 说明 |
|------|---------|------|
| `harness-me` / `harnessing` | 需求不清晰时 | 需求拷问引擎，帮用户打磨需求 |
| `diagnosing-bugs` | 线上出 Bug 时 | 先建立稳定复现的反馈循环，再分析根因 |
| `handoff` | 对话上下文快满时 | 将工作上下文压缩为交接文档 |
| `arch-review` | 需要架构体检时 | 扫描代码库，发现架构摩擦点 |

## 状态机

每个变更通过 `change.md` 的状态字段驱动流转：

```
draft → analyzing → coding → testing → reviewing → ci → verifying → done
```

详见 [变更管理](change-management.md)。
