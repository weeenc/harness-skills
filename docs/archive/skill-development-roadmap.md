### 📌 Skill 01：`/tech-design` 技术方案生成（施工图）

| 项 | 内容 |
|---|---|
| **出处** | docx 第四章整章《技术方案是质量的前置卡口》 |
| **缺口依据** | `iterations/_TEMPLATE/solution.md` 已存在，`coding-skill` 按 `开发流程规范.md §2.2` 强制"solution.md 未确认前禁止编码"，`expert-reviewer` 逐条核验 REQ→solution 承接——**模板有消费者、无生产者**，方案质量完全取决于临场发挥 |
| **核心功能** | 输入：`harnessing` 产出的规格卡 + `owner.md`（架构分层/构建命令/工具链）；输出：满足五条硬纪律的 `solution.md`（施工图） |

**五条硬纪律（不可降级）：**

1. **按依赖图排序，不按重要性排序**：数据库/存储 → 协议/接口 → 业务逻辑 → 调用方/前端；严禁出现"步骤 2 依赖步骤 5 才创建的东西"；
2. **垂直切片优先**：一个切片 = 建表 + 接口 + 最小可用逻辑，每个切片后系统处于可编译、可验证状态；
3. **任务粒度控制**：单步预计触碰 >5 个文件、或跨 >2 个独立子系统必须拆分；步骤标题出现"并且 / 同时"即视为两步；
4. **插入检查点**：每 2~3 步写入明确验证锚点（如"此处应能 `go build ./...` 通过""此处接口应能跑通基本 CRUD"）；
5. **对抗式自审**：站在"假设作者过度自信"视角找茬，输出「这个方案最可能错在哪 / 未言明的假设 / 未处理的边界」。

**配套机制：**
- **待确认问题池**（docx："不确定的事提前暴露，不让模糊进入开发"）：不确定点分**产品/技术**两类收集，支持**选择题 + 开放题**，用户逐题回答后才放行进入 `coding-skill`；
- **已确认问题防回流**：确认过的答案写回 solution.md 决策摘要，编码阶段不得重新打开已关闭问题。

**复用/依赖**：`harnessing`（上游规格）、`iterations/_TEMPLATE/solution.md`（载体，需补"待确认问题池"节）、`owner.md` 参数（ARCH_LAYER / RUN_CMD / TEST_CMD）、`impact-analysis`（若 P1-03 已出则作为步骤 0）。

**验收标准**：
- [ ] 给定真实规格卡，产出步骤序列逐条满足五条硬纪律（自检清单全绿）；
- [ ] 对抗自审至少输出 1 条关键风险（非模板套话）；
- [ ] 待确认问题 ≥2 道，且收答完成后才能进入编码；
- [ ] 在 go-im 实训项目跑通一次（验收样例可复用实演需求）。

**工作量**：M（1~2 天）
**落地文件**：`skills/harness-core/skills/tech-design/{SKILL.md, templates/solution.md.tpl}` + `docs/skills/tech-design.md` + 6 语言参数表补 TECH_DESIGN 相关占位符 + 专栏一篇（第四季风格）

### 📌 Skill 02：`/feasibility-check` 需求可行性评估与四象限分类

| 项 | 内容 |
|---|---|
| **出处** | docx 第三章"什么样的需求会通过可行性评估" + 第九章"能力边界四象限" |
| **缺口依据** | 当前任何需求（含需 DBA 审批的 DDL、跨仓库联动、资金流）都会平等进入全自动 6 阶段流水线，能力外需求在**后期**才暴露失败 → 违背 docx「把注定会在开发阶段卡住的需求拦在上游」的**保护机制**原则 |
| **核心功能** | 开工前（`tech-design` 之前）对精炼需求做**评估 + 分类**，输出《需求评估卡》 |

**评估维度（7 维，合计 100 分，<60 拦截并给补救建议）：**

| 维度 | 权重 | 评估问题 |
|---|---|---|
| 需求清晰度 | 20% | 功能点 / 业务规则 / 验收标准是否明确 |
| 仓库匹配度 | 20% | 是否落在已支持语言/框架的仓库内闭环 |
| 改动范围 | 15% | 估算文件数 / 模块数，是否单仓库内 |
| 技术复杂度 | 15% | 是否涉及新中间件 / 架构调整 / 复杂算法 |
| 外部依赖 | 10% | 是否需要 DBA / 外部系统 / 审批流 |
| 风险等级 | 10% | 资金流 / 核心安全链路 / 数据迁移 |
| 交付形态 | 10% | 标准接口 / UI / 需灰度发布 / 需数据回填 |

**四象限判定输出（不止打分，还要给执行模式）：**

- **象限① 直接做** → 全自动流水线，人只需最终验收；
- **象限② 风险协同**（如简单 DDL 需审批）→ 在链路中插入"人工审批"门禁点；
- **象限③ 复杂度协同**（多文件 / 需人拆解）→ 先 `tech-design` 由人确认方案后再编码；
- **象限④ 暂不支持**（跨仓联动 / 资金安全 / 大规模重构）→ **拦截**并给出人工处理路径。

**配套**：支持/不支持清单**版本化**存储（`rules/能力边界清单.md`），成功/失败案例回写（衔接 P3 月度校准模式）。

**复用/依赖**：`harnessing` 输出、`apply-harness` 检测结果、`owner.md`。

**验收标准**：
- [ ] 对能力清单外需求（跨仓库 / DDL / 资金流样例）能稳定拦截并给出明确理由；
- [ ] 对清单内需求判定为"直接做"，不误伤；
- [ ] 四象限输出含"人在哪个节点介入"的具体建议。

**工作量**：S~M（1 天内）
**落地文件**：`skills/harness-core/skills/feasibility-check/` + `rules/能力边界清单.md` 模板 + 文档 + 专栏

### 📌 Skill 03：`/impact-analysis` 影响面与关联修改清单

| 项 | 内容 |
|---|---|
| **出处** | docx 第七章"异常识别与干预"真实案例（舆情标签拆分**漏改关联巡检 Skill** → 入库 Bug）+ TAB 实验数据（前置质量检查**额外发现 30% 遗漏影响点**） |
| **缺口依据** | docx 结论："这种遗漏不是 AI 能力不足，而是它缺乏全局视角"。`harness-relate` 是**事后**变更关系链管理，缺**开工前**的全局视角扫描 |
| **核心功能** | 开工前扫描本次改动波及的**关联物**，输出两类清单 |

- **需同步修改清单**：代码调用点（反向依赖）、配置文件、监控/巡检规则、文档、测试 fixture、下游消费方；
- **发现但不碰清单**：范围外但值得改进的点，记录进变更摘要，交评审阶段处置（与增强 E2 呼应）。

**复用/依赖**：`arch-review`（依赖图/浅模块）、`harness-relate`（关系链）、`expert-reviewer`（评审时核验清单闭环）。作为 `tech-design` 的**步骤 0**，也可独立调用。

**验收标准**：
- [ ] 对"标签拆分"类样例能扫出被遗漏的关联模块（可用 im 群聊项目的关联模块做验证样例）；
- [ ] 清单产出后，`expert-reviewer` 可核验"每个『需同步修改』项都有对应变更或明确不做理由"。

**工作量**：M（1~2 天）
**落地文件**：`skills/harness-core/skills/impact-analysis/` + `changes/_TEMPLATE/` 增"影响面"节

### 📌 Skill 04：`/knowledge-aging` 知识老化与退场治理

| 项 | 内容 |
|---|---|
| **出处** | docx 第八章"知识老化与退场"（"过期的知识污染上下文，比没有知识更危险"）三道防线中的前两道 + 蒸馏置信度机制 |
| **缺口依据** | `knowledge-health` 只做**静态**健康检查（重复/冲突/失效链接）；资产**没有生命周期**：无 TTL、无"AI 发现注入知识与实际不符"的反馈通道、无置信度分级 |
| **核心功能** | |

- **TTL 扫描**：wiki 资产支持 `ttl` / `owner` 字段，到期自动进待复核队列，未复核则降置信度 → 归档/退场；
- **knowledge_feedback 通道**：在 `harness-retro` / `harness-ship` 中埋采集点——AI 在工作中发现注入知识与实际代码/架构不符时上报，自动降该资产置信度或触发人工复核；
- **置信度分级**：蒸馏入库资产带 `confidence (0~1)`，低于阈值进人工审核队列（衔接 docx"低的进人工审核"）。

**复用/依赖**：`knowledge-health`、`harness-retro`（回流/复盘）、`wiki/_TEMPLATE/` 模板加 TTL 字段、`wiki/知识库治理规则.md`。

**验收标准**：
- [ ] 构造一条已过期资产，扫描后进入待复核队列；
- [ ] 通过 feedback 上报一条"与代码事实不符"知识后，其置信度下降；
- [ ] 与 `knowledge-health` 合并为**同一入口**（命令分诊），不新增第二条健康类命令。

**工作量**：M（1~2 天）
**落地文件**：`skills/harness-core/skills/knowledge-aging/`（或并入 knowledge-health 模块）+ wiki 模板加字段 + retro/ship 埋点

### 📌 Skill 05：`/human-review-guide` 意图级人工审查引导

| 项 | 内容 |
|---|---|
| **出处** | docx 第六章"审查对象变了，但审查标准没变" + 第七章"代码 Review 从行级向意图级升级" |
| **缺口依据** | `expert-reviewer` 是 **AI 审 AI**；但对于需人介入的变更（象限②③、资金/安全类），**给"人"的审查引导物缺失**——人容易退回逐行挑格式（docx 批判的"风格偏好"顽疾） |
| **核心功能** | 输入 `review.md` + 变更内容，输出**给人看的核查清单** |

- 3~5 个重点核查项：跨模块交互是否正确、边界条件是否处理、安全影响面是否评估、是否准确实现需求意图（非逐行阅读）；
- 明确放行标准：**改善即批准**——风格差异/命名偏好不阻塞，真实功能/安全/意图偏差才阻塞；
- 生成可直达的一次 review 会话（附所需上下文）。

**复用/依赖**：`expert-reviewer` 输出（review.md 为输入）、`impact-analysis` 清单、`handoff`。

**验收标准**：
- [ ] 对同一变更，输出清单聚焦 ≥3 个意图级问题而非格式问题；
- [ ] 与人走完一次评审后，结论可映射回 review.md 的 🔴/🟡/🔵 分级。

**工作量**：S~M（1 天内）
**落地文件**：`skills/harness-core/skills/human-review-guide/` + `docs/skills/` 文档

### 📌 Skill 06：`/repo-discovery` 仓库匹配与能力地图
- **出处**：docx 九阶段全链路第 2 环"仓库匹配"（需求 → 正确仓库/服务）。
- **现状**：`apply-harness` 只做单仓库内语言/框架识别；多仓库组织下"这个需求该落到哪个仓库"无技能承接。
- **形态**：**轻量版先行** = 维护一份仓库指纹表（`.harness/repo-map.yaml`：路径关键词 → 仓库职责/语言/框架），按需求文本打分匹配；重版（多仓索引/语义图谱）放平台侧（见 P3）。
- **验收**：给定"支付对账超时"类需求，能从指纹表定位到正确仓库及模块路径。

### 📌 Skill 07：`/onboard-newbie` 新人上手引导
- **出处**：docx 第十章"新同学通过平台做第一个需求，直接站在团队积累上工作"；"人走了知识还在"。
- **现状**：wiki/文档齐全，缺"引导新人把积累用起来"的流程。
- **形态**：按序执行——读 CONTEXT.md → 过 owner.md 与 5 条规则 → 跑一个最小练习需求（harness-me → deploy-verify 全程）→ 读团队 wiki 高层 + 最近 2 条 ADR → 产出《我的理解》交接小结。
- **验收**：新人在无导师陪跑下独立走通一次完整流水线并产出交接小结。

## 六、验收总纲（每个新 Skill 必须满足 harness 自身标准）

1. **可编译/可消费**：SKILL.md 结构合规，占位符渲染后 6 语言均可运行；
2. **单一事实源**：模板放 `harness-core/skills/`，语言包不复制内容；
3. **有门禁可测**：技能产出（评估卡 / solution.md / 影响面清单 / 核查清单）都有明确验收点，能被 `expert-reviewer` 或人工按清单核验；
4. **文档齐全**：`docs/skills/<name>.md` + README 技能清单更新 + 专栏文章一篇（第四季风格）；
5. **实演验证**：在 go-im 实训项目完整走通一次，产出物留档（参照同级 `prd-ingestion/docs/article-harness-in-real-project.md` 的做法）。
