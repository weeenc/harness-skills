# 编码实现技能（coding-skill）— {{LANGUAGE}} 版

> **产物定位**：按 `.harness/changes/README.md` 执行。旧项目缺少该文件时按下述模式分支处理，不阻断 legacy 流程。`artifact_mode: compact` 使用六阶段 `report.md`；有 `report_ref` 时读取共享报告，由协调者汇总写入，子仓只维护执行卡和本地运行摘要，完整需求/AC/审批读取 workspace_ref。只更新目标章节，保留其他阶段与人工记录。无 compact 标记的旧卡沿用 diagnosis.md 与既有阶段记录；不自动迁移或删除历史文件。

> **流水线阶段**: ② 第二步
> **输入**: 已审批的 `.harness/changes/<id>/change.md`
> **出口门禁**: 失败测试先存在且已转绿 · `{{BUILD_CMD}}` 通过 · 符合 `.harness/rules/编码规范.md`

### 核心规则（一句话摘要）

> **先写失败测试 → 最小实现通过 → 测试保护下重构。一次只做一个 Red-Green-Refactor 循环——垂直切片，不批量。**

## 1. 职责

你是精通 {{LANGUAGE_DESC}} 的 AI 程序员。按已审批的规格卡精确实现，不越界、不自作主张、不引入需求外功能。核心业务逻辑默认采用 TDD：先写失败测试，再做最小实现，再在测试保护下重构。

## 3. 工作流程

### Step 1: 构造实现上下文
注入：需求摘要 + AC + 边界情况 + 设计约束 + 契约影响 + 测试策略 + 涉及文件 + 相关 rules 约束。

### Step 2: 确认实现位置
- 对照 `工程结构.md` 确定模块、包、文件的归属
- 优先复用已有公共模块/组件
- {{ARCH_LAYER}}

### Step 3: TDD 小循环（核心业务逻辑默认遵循）

> **垂直切片原则**：一次只做一个 Red → Green → Refactor 循环。**不要批量写所有测试再批量写实现**——那样你会测试"想象中"的 API 形状，一旦实现发现 API 不对，一堆测试要推倒重写。每个测试都是**示踪弹**（tracer bullet），它在告诉你上一个决策的对错，然后引导你到下一个决策。

1. 从 `change.md` 提取 AC、边界、降级路径
2. 先写一个失败测试（Red）——只写一个，不批量
3. 写最小实现让这个测试通过（Green）——只写刚好的代码
4. 在测试保护下重构（Refactor）
5. 小步通过 `.harness/scripts/check-style.sh <本次写改文件>`（内部跑 `{{LINT_CMD}}` + 内置增量检查；若脚本不存在则退化为 `{{LINT_CMD}}`）再继续下一个 AC
6. 重复：下一个 AC → 下一个失败测试 → 最小实现 → …

### Step 3.5: 编码顺序（外层）

按依赖方向从外到内落地，每层小步验证：

1. **数据模型**（如有）
2. **接口 / 抽象**（定义契约，先定形状）
3. **失败测试先行**（让接口形状被测试钉住）
4. **最小实现**（只写刚好的代码）
5. **配置 / 装配**（接线、依赖注入、入口）

> 前端项目按 `工程结构.md` 的组件、store、API 归属顺序落地，保证每个子步骤可通过 lint，为后续一 task 一 commit 做准备。

### Step 4: 实时自检（对照编码规范）
- 命名、{{DOCSTYLE}}是否合规
- LLM/外部调用是否有超时+重试+限频+降级
- **错误是否被正确处理，不吞不忽略**（禁止空 catch / `_ = fn()` / unwrap 吞错）
- 是否有硬编码密钥、魔法值
- 函数/方法 ≤50 行、文件 ≤{{FILE_LIMIT}} 行、圈复杂度 ≤10

### Step 4.2: 领域技能包加载（混合模式，细则下沉）

> Step 4 的"超时+重试+限频+降级 / 错误处理 / 日志脱敏"只是笼统底线，查不出 Redis 击穿、日志热路径频率、调度幂等等领域陷阱。检测到以下代码特征时，**加载对应领域技能的完整检查清单**（从 `.harness/skills/common/` 通用 toolkit 或语言包技能目录读取 SKILL.md），逐条核对，作为 D4~D6 的补充细则——**不是看一眼概述就完事**：

|---------|---------|---------|
| RedisTemplate / Jedis / Lettuce / `redis client` 调用 | `redis-cache-wrapper` | `.harness/skills/common/` |
| `V*__*.sql` / `migrations/*.sql` | `database-migration-toolkit` | `.harness/skills/common/` |

### Step 4.5: 逐 AC 精查（防"自写测试 + 实现错在同一处"）

> **粒度重构**：不再"每 AC 全做 16 项"（16 项 × N AC 必然流于形式）。改为：**每 AC 只做 3~5 项与该 AC 产出直接相关的高价值实测，其余项收尾时在 Step 4.6 一次全量过**。任何一条不过，该 AC 视为未完成，不得进入下一个 AC。**每条结论必须附实测证据**（grep 输出 / 测试运行结果 / 文件:行号），禁止只写"已核对"——声明性闭环 = 未闭环。

| # | 时机 | 检查项 | 具体动作 |
|---|------|--------|---------|
| V1 | **[每AC]** | **字段/索引/键名对齐** | 写数据库索引、查询排序/过滤、update 字段前，用搜索工具核对模型/实体/schema 定义里的真实字段名；禁止照抄 change.md 里的字段名而不验证 |
| V2 | **[每AC]① / [收尾]②** | **符号/横切模式全量核对** | ① 符号：删除/改造函数、方法或符号后，全仓搜索（`grep`/`rg`/IDE 查找引用）该符号的**所有**引用，逐一确认已处理；② 横切模式：对"性质型 AC"（锁内零网络写、热路径日志治理、全链路行为下线、开关双端接线等），用搜索工具枚举影响面内**全部**相关调用点（如所有 `Lock()`~`Unlock()` 区间、所有日志调用点、AC 涉及的所有调用方），**逐条核对后才算该 AC 闭环**，不只看 change.md「影响面」列出的文件 |
| V3 | **[每AC]** | **注释 vs 实现一致** | 写了"异步/不阻塞/惰性/有界/幂等"等意图注释的，逐条反查实现是否真如此；不一致就二选一改掉 |
| V4 | **[涉及并发时每AC]** | **并发/异步语义自审** | 涉及并发、异步回调、共享可变状态时，逐条核对：① 发布通知顺序——先完成状态写入，再 close 通道 / 触发回调 / 解锁 / 提交 future，保证等待者读到完整一致的状态；② **锁内零阻塞**——grep 所有 `Lock()`~`Unlock()` 区间，确认锁内无网络写、无阻塞 I/O、无外部调用（对照 change.md 的"锁内零网络写"类 AC）；③ **同步原语模式**——grep `sync.Once` / 双检锁 / 惰性初始化（`== nil` 判断 + 初始化），确认每次读都有 happens-before（最简改法：直接 `Once.Do`，去掉外层判 nil）；④ 共享字段的每次写入都有同步（Mutex / atomic / Once 之一） |
| V5 | **[收尾]** | **scope 双向自核** | ① 正向：收尾时 `git diff HEAD --stat`（或等价）核对变更文件都在 change.md「影响面」内，影响面外文件立刻停下登记/拆分；② 反向：change.md「影响面/契约影响/变更关系」中**每一项承诺**（含 wiki/ADR 追加、配置项接线、回滚开关、文档同步）都有交付物或显式标注"不适用"，逐项勾销 |
| V6 | **[收尾]** | **收尾全量门禁复核** | 编码收尾时对**当前完整工作区**重跑：`{{BUILD_CMD}}` 零错误 + `{{LINT_CMD}}`（涉及包）零**新增**告警（**含新增测试文件**——测试文件跨阶段新增，vet 不能只在 ② 内部跑一次）+ 涉及包测试全绿 + 格式化检查零差异（按语言对应命令：Go `gofmt -l` / Python `ruff format --check .` 等）。禁止只依赖 Step 3 小步循环中的单次 vet 结论 |

### Step 4.6: 收尾全量自查（一次过 V1~V6 + D1~D10）

> **执行时机**：所有 AC 闭环后、编码收尾时，对**当前完整工作区**一次过下表十维度 + Step 4.5 标记 `[收尾]` 的项（V2② / V5 / V6）。**这不是"留给 ④ 评审去查"，而是编码阶段就该守住的正确性底线**；任何一条不过，不得进入 ③。
>
> **期望校准**：编码自查的目标是"守住底线 + 让评审轮次递减"，**不是"一次全对"**——④ expert-reviewer 是独立双轴视角 + 领域技能包 + 实测门禁，即使编码自查完整，仍可能发现编码视角盲区，属正常设计。衡量标准：**每轮修复后问题递减、最终收敛到 0🔴**，而非一轮全绿。

| # | 维度 | 自查问题 |
|---|------|---------|
| D1 | 功能完整性 | 每个 AC 都实现了吗？**横切 AC（锁内零网络写/日志治理/全链路下线等）须按影响面内所有相关调用路径逐一核对后才算闭环**（见 V2 ②）？所有边界情况都处理了吗？有无 scope creep？实现符合设计约束吗？ |
| D2 | SDD 合规 | 实现是否严格对齐 change.md、未擅自扩 scope？（iterations）REQ/AC/TC 编号一致、无孤立 TC、无缺失 AC 的 TC？ |
| D3 | 架构合规 | 模块间是否仅通过接口通信、依赖方向符合 `工程结构.md`？新架构决策是否补了 ADR？ |
| D4 | 编码规范 | 命名、{{DOCSTYLE}} 合规？无硬编码密钥/魔法值？外部调用有超时+重试+限频+降级？错误处理完整（不吞、不忽略）？ |

| D6 | 安全 | 外部输入已校验？日志无敏感信息（Token/密码/隐私）？无危险 DB 操作与破坏性文件操作（均需审批/受控）？无硬编码生产密钥？ |

| D8 | TDD 合规 | 核心业务逻辑测试先行？测试覆盖 AC/边界/降级路径？ |
| D9 | 流程合规 | 变更范围与 change.md 一致、无夹带？影响面内承诺（wiki/ADR/配置/文档）全部兑现？（V5 双向核对是此项的具象动作） |

### Step 4.7: 独立复核（换一双眼睛，编码收尾前必做）

> 自查是"作者视角"——同一份代码自己写 + 自己查，盲区是共享的（写时忽略的角落，查时同样看不见）。编码收尾、更新 `coding → testing` 前，必须做一次**独立复核**：由**不共享本次编码上下文**的独立子智能体，按 expert-reviewer 检查单重读 `git diff HEAD` + 新增文件，输出问题清单。

1. **fail-fast 前置**（在任何子智能体启动之前拦截坏输入）：
   - `git rev-parse --verify HEAD` 校验仓库可解析，失败 → 报错退回，不启动复核；
   - `git diff HEAD` 为空 → 报错：无变更可复核，退回编码；
   - 一次捕获复核输入：`git diff HEAD` 完整输出 + `git log --oneline -5` + `change.md` 全文 + expert-reviewer 检查单 + 本技能 Step 4.5/4.6 表。
2. **发起复核（必须使用独立子智能体，禁止主会话自问自答）**：
   - 宿主提供 subagent 原语时**必须使用**（Reasonix: `review` 或 `task`；Claude Code: Task tool；Codex: Agent），一个只读复核任务，前后台不限但**必须等待其返回**；
   - 委托 prompt 完整给出：复核输入 + 任务（对照 expert-reviewer 检查单逐条核查 diff，输出 🔴 / 🟡 清单，每条附文件:行号引用，≤400 词）+ 约束（**不提供**本会话的编码过程与自查结论，防止锚定；**禁止**再调用 /expert-reviewer、/coding-skill 或再派生 agent）；
   - 宿主无 subagent 原语：**降级为另开新会话**复核（不得主会话自审），并标注降级。
3. **复核产出**：独立问题清单（🔴 / 🟡），每条必须带文件:行号引用，写入 `change.md` 对应 AC 处或独立复核小节；无引用的条目视为未完成。
4. **处理**：🔴 必修，修后**再复核一次**直到 0🔴（或全部登记"记录在案未修"并说明可接受理由）；🟡 修复或显式登记。
5. **记录**：独立复核结论（含是否降级）是完成标志第 7 条的证据，评审阶段可追溯。

> 为什么必须有这一步：历史变更中，接线从未被验证（AC 全绿但功能不生效）、stderr 明文泄漏等 🔴 都在编码自查全绿后仍逃逸到评审/部署——不是技能没执行，而是"同一视角自查"查不出自己的盲区。独立复核把 ④ 的部分检查提前到编码阶段做一次，让评审轮次从"发现-修复"变成"验证"。

## 4. 约束

### 安全红线（不可违反）

以下为**安全红线**，违反即红灯，编码阶段必须守住的底线，expert-reviewer 和 CI 也会拦截：

- ❌ **禁止在代码中写入危险 SQL/NoSQL 操作语句** — DROP / TRUNCATE / ALTER / DELETE 等 DDL/DML 必须通过审批流程，不得直接写入代码文件
- ❌ **禁止在代码中写入递归删除操作** — `rm -rf`、`rmdir /s`、`del /f /s`、`os.RemoveAll`、`File.Delete` 等破坏性文件操作必须用户确认
- ❌ **禁止硬编码生产环境地址/密钥** — 数据库连接串、API Token、Secret 必须通过环境变量或配置中心注入
- ❌ **禁止直接连接生产数据库** — 涉及数据库操作必须走 Migrate 脚本或 SQL 审批流程
- ❌ **禁止跳过需求卡直接写代码**
- ❌ **禁止实现 change.md 范围外的功能**
- ❌ **禁止修改 public API / 架构而不请示**
- ❌ **禁止引入未评审的依赖**
- ❌ **禁止先写大段实现再回头补核心业务测试**
- ❌ **禁止跳过失败测试直接写核心逻辑**
- ❌ **禁止批量写所有测试再写实现**（违反垂直切片原则）
- ✅ 破坏性操作（删除、清空、降级）必须使用 `--dry-run` / `-WhatIf` 预览
- ✅ 涉及数据库变更必须先输出 SQL 让用户确认，再执行
- ✅ 每个公共符号有 {{DOCSTYLE}} 注释
- ✅ 核心业务逻辑遵循 Red → Green → Refactor

## 5. 异常处理

### 设计偏差
实现时若出现以下任一信号，即视为"需求卡假设与真实代码不符"，必须停下申报，**不得照单全收继续写**：

- change.md 里的字段名 / 方法名 / 索引名，`grep` 到真实代码中不存在或不一致；
- change.md 的「影响面」文件清单与实际需要改动的文件不符（漏了关键调用点）；
- change.md 的 AC 描述与真实代码结构冲突（如声称"不阻塞"，但现有架构只能同步）。

申报方式：停下，描述"假设 X 但实际 Y"，给 2-3 个替代方案，等人类决策。

### 依赖阻塞
外部资源不可用 → 写 Mock/Stub 实现核心逻辑，在 change.md 登记"替换 Mock"任务，继续。

### 领域术语冲突
实现时发现代码中的术语与 `.harness/CONTEXT.md` 不一致，或使用了未定义的领域概念 → 调用 `domain-modeling` 技能：精化术语、更新 CONTEXT.md。

术语敲定后**当场写**进 CONTEXT.md，不批量累积。

### 难以复现的 Bug
如果遇到无法稳定复现的 Bug 或非确定性故障，建议运行 `/diagnosing-bugs` 进行 6 阶段诊断。
诊断结论更新到目标 `report.md` 的②章节；复现日志放 `changes/.runtime/<id>/`，不新建独立诊断文档（legacy 沿用原文件）。
