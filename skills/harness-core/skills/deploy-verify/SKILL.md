# 部署验证技能（deploy-verify）— {{LANGUAGE}} 版

> **产物定位**：按 `.harness/changes/README.md` 执行。旧项目缺少该文件时按下述模式分支处理，不阻断 legacy 流程。`artifact_mode: compact` 使用六阶段 `report.md`；有 `report_ref` 时读取共享报告，由协调者汇总写入，子仓只维护执行卡和本地运行摘要，完整需求/AC/审批读取 workspace_ref。只更新目标章节，保留其他阶段与人工记录。无 compact 标记的旧卡沿用 verify.md 与 archive.md；不自动迁移或删除历史文件。

> **流水线阶段**: ⑥ 第六步 · 收口
> **输入**: 通过 ⑤ CI 的构建
> **产出**: 目标 `report.md` 的「⑥ 部署验证与归档」章节
> **出口门禁**: 冒烟 + 健康检查通过，有回滚预案

### 核心规则（一句话摘要）

> **"CI 绿"不等于"线上可用"。确认页面/服务可正常加载与访问、健康检查 UP、核心链路通、降级链路通、有回滚预案。**

## 前置检查

1. **定位目标 change**（按 `.harness/rules/变更定位规则.md`）：
   - 扫描 `.harness/changes/*/change.md`，过滤 `status: verifying`
   - 用户已指定 `<id>` → 校验该 change 状态是否为 `verifying`，否则报错
   - 恰好 1 个 → 自动选中
   - 0 个 → 报错：无处于 `verifying` 状态的 change，退回 ⑤ unit-test-ci
   - ≥ 2 个 → **列出候选清单（id + 标题 + 摘要），停下请用户选择**，不得擅自默认取第一个
2. **锁定验证范围**（确保每次验证同一份代码）：
   - **规则**：使用 `git diff HEAD` 作为验证范围，包含工作区未提交的变更
   - 如果 `git diff HEAD` 为空，报错：无变更可验证，退回 ⑤ unit-test-ci
   - 在报告开头明确标注验证范围（文件数、增减行数、分支名）
3. **加载动态事实来源**：读 `.harness/动态事实来源.md`，确认环境/日志/指标/工作项等动态事实的权威来源与连接方式，供验证与回滚时查询真实状态
4. 缺前置 → 退回 ⑤ unit-test-ci

## 1. 职责

你是上线把关人。确认变更在真实/类生产环境**真的能跑、关键链路真的通**，且出问题能快速回滚。"CI 绿"不等于"线上可用"。

## 2. 工作流程

### Step 1: 准备环境

按 `.harness/rules/工程结构.md` 中的启动方式准备环境：

```bash
{{BUILD_CMD}}   # 已在 CI 验过测试
{{RUN_CMD}}     # 启动服务（具体命令见工程结构.md）
```

### Step 2: 健康检查

```bash
{{HEALTH_CHECK_CMD}}       # 期望 UP / {"status": "ok"}
curl {{METRICS_ENDPOINT}}  # 指标可读
```

### Step 3: 冒烟测试（关键链路）

| 链路 | 验证点 |
|------|--------|
| 页面/服务可用 | 页面正常加载不白屏、无 JS 报错（前端）；健康检查端点 = UP（后端） |
| 核心链路 | 端到端主链路（如登录 → 首页 → 关键操作）返回预期结果，控制台无 4xx/5xx |
| 降级 | 模拟外部依赖故障，确认降级生效 |

### Step 4: 可观测性核验

- 链路追踪有完整 trace（后端）；前端无 JS 报错、控制台无 4xx/5xx
- 关键指标/埋点上报告警正常
- 日志为结构化 JSON，无敏感信息泄露

### Step 5: 回滚预案

- 记录上一个稳定版本 tag / 构建产物 / 镜像
- 明确回滚命令（见 `.harness/rules/工程结构.md`/发布约定，如前端 CDN 切换）与触发条件
- 回滚后验证核心链路恢复；确认无破坏性数据迁移

## 3. 输出格式（compact 更新 report.md 的⑥章节）

legacy 沿用 verify.md。记录实际版本、环境、traceId/业务断言与动态事实回查；下方成功项只在真实执行后填写，不覆盖同章节已有人工确认。

> **⛔ 强制规则：无论验证结果是否通过，都必须将完整报告写入目标 `report.md` 的「⑥ 部署验证与归档」章节。**
> **未写入 report.md 不得进入下一步。**

```markdown

### 总览
- 验证范围: `git diff HEAD` — N 个文件，+N/-N 行
- 分支: <branch-name>

### 环境
- profile: dev / 镜像: …

### 健康检查
- [x] /health = UP

### 冒烟测试
| 链路 | 结果 |
|------|------|
| 核心 API | 🟢 |
| 降级 | 🟢 |

### 回滚预案
- 上一稳定版本: <tag>
- 回滚命令: <cmd>

### 结论
✅ 验证通过，变更可交付 / ❌ 失败，退回 …
```

## 4. 完成标志

无论验证结果如何，**必须先完成**：

1. ✅ 将完整报告写入目标 `report.md` 的「⑥ 部署验证与归档」章节
2. 在同一⑥章节填写交付与知识回流清单（业务→wiki、链路→tech、决策→ADR、术语→CONTEXT）；沿用原知识维护逻辑，compact 不另建 archive.md。
3. 然后根据检查结果执行分支：
   - **验证通过** → 更新 `change.md` 状态 `verifying → done`，变更交付完成，同步相关 `.harness/wiki/`（业务规则）与 `.harness/tech/`（技术链路）文档
   - **验证失败** → 退回 ⑤ unit-test-ci（report.md 作为排查参考依据）
