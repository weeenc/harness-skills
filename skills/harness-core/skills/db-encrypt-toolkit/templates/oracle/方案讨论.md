# 方案讨论 —— 数据库敏感字段加密：「视图 + 触发器 + 定时任务」路线（跨库）

> 版本：v1 · 配套验证脚本见同目录（00_setup / 01_verify_dml / 02_verify_query / 03_verify_perf）
> 场景：密评 / 等保要求下对敏感字段（姓名、手机号、证件号等）做存储加密，且**应用尽量免改造**。
> 本文档结论以 Oracle 为详细基准，并给出 15+ 数据库的能力矩阵与适配要点。

---

## 1. 路线对比总览

| 维度 | 路线 A：视图 + 触发器 + 定时任务 | 路线 B：协议代理（SQL 透明加密代理） |
|---|---|---|
| 实现思路 | 原表改名为备份表 → 拆 A1（密文+防篡改哈希）/ A2（明文+辅助列）→ 建**同名视图**承接应用 SQL → INSTEAD OF 触发器把 DML 拆落 A1+A2 → 定时任务做增量加密/洗数 | 应用与数据库之间插入代理，解析 SQL，按策略对敏感列写时加密、读时解密 |
| 应用改造 | 零改造（SQL 相同、库名相同） | 只改连接串/端口，业务代码零改造 |
| 库内是否留明文 | 有（A2 明文表，Excel 已注明） | 无（库内仅密文） |
| 性能 | 查询≈原表（简单视图）、写入慢 2~5x、批处理不可接受 | 每条 SQL 解析+加解密，损耗中等偏高，需压测 |
| 主要风险 | 复杂语句适配、TRUNCATE/MERGE 等限制、触发器错误 | 代理高可用、语法覆盖不全、部署与网络改造 |
| 适用 | 表小、预算有限、仅 Oracle/PG/SQLServer 等支持 INSTEAD OF 的库 | 大表高并发、需库内无明文、多语法复杂 SQL |

**本文档详述路线 A**；路线 B 的对比列在配套 Excel 中已补全（见 `技术路线对比-视图+触发器+定时任务与协议代理.xlsx`）。

## 2. 路线 A 原理（以 Excel 表结构为例）

```
原表 A (id, f1 敏感, f2) ──改名──> A_BAK（隐藏，仅用于洗数与回滚）

拆分：
  A1 (id, f1_cipher 密文, f2, f1_h 防篡改哈希)   ← 定时任务/触发器写
  A2 (id, f1_plain  明文, fn 辅助列)              ← 模糊/大小写/排序查询兜底

新建同名视图 A (id, f1 := 解密(f1_cipher), f2)
  + INSTEAD OF 触发器：INSERT/UPDATE/DELETE 拆落 A1+A2（应用无感知）

定时任务（增量）：把新/改明文加密进 f1_cipher，重算 f1_h
```

- 应用 SQL 不变：`SELECT/INSERT/UPDATE/DELETE FROM A` 全部落到同名视图；
- 敏感列读取 = 解密函数逐行转换（**无法索引、无法下推谓词**）→ 过滤/排序/聚合一律走 A2 的辅助列与照搬索引；
- 数据字典 / 报表 / ORM 看到的是「视图」，部分工具行为会变。

## 3. 跨数据库能力矩阵（15+ 库，选型决策表）

> 「INS-OF」= 视图上的 INSTEAD OF 触发器；「原生可更新视图」= 无需触发器即可 DML 的简单视图；「内置加密」= 内置 AES/加解密 SQL 函数；「原生调度」= 自带 SQL 定时任务能力。

| PostgreSQL | PG | ✅ (PG 9.1+) | ✅ | ✅ pgcrypto | ✅ pg_cron(扩展) | 🟢 A | RULE 可作旧方案 |

## 4. 各库实现要点（方言差异）

- **Oracle / PostgreSQL / SQL Server**：语法与行为见配套验证脚本；三库均支持视图 INSTEAD OF 触发器，验证脚本（Oracle 版）思路可直接平移：把 `DBMS_CRYPTO` 换成 `pgcrypto` / SQL Server 的 CLR 或用系统函数。
- **PG**：`CREATE TRIGGER ... INSTEAD OF INSERT OR UPDATE OR DELETE ON view`（PG 9.1+）；加密用 `pgcrypto` 的 `encrypt/decrypt(AES)`；定时任务装 `pg_cron`。
- **SQL Server**：`CREATE TRIGGER trg ON v INSTEAD OF INSERT/UPDATE/DELETE`；SQL Server 无内置 AES 标量函数，方案建议：① 应用层加密写 A1 密文（触发器不用加密，只做拆分 + 哈希 `HASHBYTES('SHA2_256', ...)`）；② 或列级 Always Encrypted（另一种路线）。
- **MySQL / MariaDB**：无 INSTEAD OF 触发器 → 只能依赖"原生可更新视图"（简单视图直接 DML）。**复杂视图（多表 JOIN/聚合）不可更新**，是这类库的最大边界；若业务全是单表简单读写，视图路线可用 `AES_ENCRYPT/AES_DECRYPT` + `EVENT` 定时任务。
- **SQLite**：`CREATE TRIGGER ... INSTEAD OF INSERT ON v` 支持；加密用应用层（无内置 AES）；无原生定时任务，用应用调度。
- **CockroachDB / TiDB / Spanner / Hive / Trino / Snowflake / BigQuery / Redshift**：视图只读或无触发器 → 路线 A 不可行，直接评估协议代理 / 应用层加密 / 云侧 KMS+列加密。
- **国产库**：以"兼容哪种方言"为准（达梦=Oracle 兼容、金仓=PG 兼容、GaussDB=分模式），先跑对应方言验证脚本，再按实测调整。

## 5. 路线 A 的通用红线（跨所有数据库）

以下任一条命中，路线 A 直接否决（或必须转路线 B）：

1. **加密字段参与运算/聚合/排序/过滤**：`SUM/AVG/BETWEEN/ORDER BY/JOIN 键` 在密文上无法下推（数值、金额类字段）。
2. **批处理 DML**：`MERGE`、`INSERT...SELECT 大批量`、定期全量 UPDATE —— 触发器逐行放大，性能不可接受。
3. **`TRUNCATE` 依赖**：TRUNCATE 是 DDL，触发器拦不住（Oracle/SQL Server 直接失败；MySQL 之类的可更新视图同样拒 TRUNCATE）。
4. **外键引用链**：视图不能建 FK / 被 FK 引用，拆表后建库脚本断裂。
5. **`rowid` / 闪回 / `FOR UPDATE` / `RETURNING` 强依赖**：视图语义变化，需实测。
6. **数据字典工具强依赖**：`ALL_TAB_COLUMNS`、`information_schema`、ETL/ORM 自动 DDL 看到的物理结构变化。
7. **数据量大、写入高频的表**：增量加密窗口 + 写入放大一并放大，风险不可控。

## 6. Oracle 详细结论（配套验证脚本对应）

> 详细可跑项见 01/02/03 脚本与 README 判定表；这里给出设计结论。

**不支持的 SQL / 操作**：TRUNCATE、MERGE 到视图（受限）、视图上建普通 BEFORE/AFTER 触发器（ORA-38069）、RETURNING 与 FOR UPDATE（行为受限需实测）、外键与 rowid 依赖。

**性能结论（需实测回填）**：
- 查询：简单视图无额外 IO；**前提**是过滤/排序/聚合字段由 A2 明文/辅助列顶替并照搬索引；
- 写入：每条 DML 走触发器 + 加解密，写入放大 2~3 倍，行级 DML 慢 5~20x（脚本 P1）；
- 过滤：解密列谓词全表扫 vs 辅助列索引，数量级差距（脚本 P3）；
- 批量 UPDATE 走视图：不可接受，批处理必须直写基表（脚本 P4）。

**不停机切换**（Excel 验证点 4）：
- 顺序：建 A2/A3 并 backfill → 建同名视图 + 触发器 → 同步授权与数据字典 → 切换应用流量，全程应用零改动、无需停机；
- 关键：**增量加密窗口设计**。新写入行触发器同步写密文（无窗口）；若选择"先明文后定时任务加密"，视图 F1 写成两段式 `CASE WHEN f1_cipher IS NOT NULL THEN ... ELSE A2.f1 END` 会彻底丧失下推——只允许二选一，不可混用。

## 8. 与协议代理（路线 B）的分界建议

- **选路线 A**：仅 Oracle/PG/SQLServer/金仓等 🟢 库；表小、预算有限、应用零改造优先；能接受库内留明文。
- **选路线 B**：大表高并发、库内必须无明文、跨多库方言（TiDB/Cockroach/云数仓等 🔴）；能接受代理部署组网与改连接串的协调成本。
- **混合**：同库不同表可混合——高频大表走 B（或应用层），小表走 A；但同一库同一表不要两条路线叠加。
