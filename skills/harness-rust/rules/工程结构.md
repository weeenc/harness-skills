# 工程结构规范

> **作用域**: 定义本项目的目录组织、模块划分、依赖方向。
> **状态**: 强制 · 违反即阻断 CI

---

## 1. 顶层目录结构（Rust 项目）

```
<project-root>/
├── CLAUDE.md                  # AI 协作入口
├── README.md
├── .gitignore
├── Cargo.toml / Cargo.lock    # 依赖管理
├── rust-toolchain.toml        # 工具链版本（可选）
├── .editorconfig
│
├── .harness/                  # 🔗 Harness 约束体系
│   ├── agents/                #   Agent 定义
│   ├── rules/                 #   规则约束
│   ├── skills/                #   开发技能
│   ├── wiki/                  #   领域知识
│   └── changes/               #   变更追踪
│
├── src/                       # 源码根（lib/bin crate）
│   ├── main.rs                # 二进制入口（如有 bin）
│   ├── lib.rs                 # 库入口（核心逻辑放这里，便于测试）
│   ├── config/                # 配置加载（env + 配置文件 → 结构体）
│   ├── domain/                # 领域模型（结构体、枚举、业务规则）
│   ├── service/               # 业务逻辑层（核心）
│   ├── repository/            # 数据访问层（DB / 外部 API 封装）
│   ├── api/                   # HTTP API 层（路由、handler、DTO）
│   │   ├── handler/           # 请求处理器（薄层）
│   │   ├── middleware/        # 中间件（鉴权、日志、限流）
│   │   └── dto/               # 请求/响应数据结构
│   ├── error.rs               # 统一错误类型（thiserror/anyhow）
│   └── state.rs               # 应用共享状态（AppState）
│
├── tests/                     # 集成测试（pub API 级）
├── benches/                   # 基准测试（可选）
├── migrations/                # 数据库迁移（sqlx/diesel）
├── scripts/                   # 开发/部署脚本
├── docker/                    # Docker 配置
└── docs/                      # 项目文档
```

> **核心**: 业务逻辑放 `lib.rs`（库 crate），二进制 `main.rs` 保持薄壳——这是 Rust 项目可测试性的基础。

## 2. 模块职责与依赖方向

```
api (handler/dto)  →  service  →  domain
                        ↓
                   repository  →  (DB / 外部 API)
```

- **依赖单向**: `api → service → repository/domain`，禁止反向
- **domain 是最内核**：不依赖任何外部框架（纯 Rust 结构体 + 业务方法）
- **service 编排业务**：事务边界、业务规则、领域事件
- **repository 隔离数据源**：定义 trait，实现换 SQLite/Postgres/Redis 不影响上层
- **api 是薄层**：解析请求、调用 service、映射错误与响应，禁止放业务逻辑

## 3. 模块组织约定

| 规则 | 说明 |
|------|------|
| 一个功能一个模块 | 按领域聚合，不按技术层切目录（避免反向依赖） |
| 模块边界 | 仅通过 `pub` 接口互通，`pub(crate)` 控制内部可见性 |
| crate 拆分 | 体量增长后用 workspace 拆 crate（domain/service/transport） |
| 循环依赖 | 禁止（cargo 编译报错前先自查模块图） |

### 3.1 典型 crate 结构

```
myapp/
├── Cargo.toml                     # workspace
├── crates/
│   ├── domain/                    # 纯领域模型 + 规则
│   ├── application/               # 用例/服务编排
│   ├── infrastructure/            # DB、HTTP client、外部服务
│   └── transport/                 # REST / gRPC handler + DTO
```

## 4. 错误处理结构

```
src/
└── error.rs
    ├── AppError (enum, thiserror)   # 业务错误码
    ├── From<...> 转换              # 各层错误 → AppError
    └── 响应映射                     # AppError → HTTP 状态码
```

- 禁止在 handler 中返回裸 `Box<dyn Error>` 或 `unwrap()`
- 库函数返回 `Result<T, AppError>`，main/测试中才允许 `?` 到 `MainError`

## 5. 文件组织约束

| 约束 | 规则 | 守护手段 |
|------|------|---------|
| 文件长度 | ≤ 800 行 | cargo clippy / 人工 |
| 函数长度 | ≤ 50 行 | cargo clippy |
| 圈复杂度 | ≤ 10 | cargo clippy |
| 依赖审计 | 0 高危漏洞 | cargo-deny / cargo audit |
| 竞态检测 | unsafe 经审批、共享状态加锁/tokio 同步原语 | 人工 + loom（如并发逻辑） |

---

## 6. 新增模块/feature 的目录约定

- 新领域模块 → 在 `src/` 下新建子模块，并在 `lib.rs` 声明
- 新 API 端点 → 在 `src/api/` 增 handler + 路由注册，DTO 对齐契约
- 新数据源 → 定义 `repository` trait + 实现，迁移脚本进 `migrations/`
- 新需求 → 在 `.harness/changes/<id>/` 建档
## 7. 架构审查关注点（arch-review 引用的语言特有检查项）

- **trait 设计** — 是否有过于宽泛或过于细碎的 trait（违反 ISP）？
- **模块边界** — crate/模块划分是否符合单一职责，依赖方向是否单向？
- **{{FRAMEWORK_NAME}} 布局** — handler/service/repository 分层是否正确？
- **所有权与借用** — 是否有不必要的 clone()、生命周期过度复杂、unwrap() 滥用？
- **异步模型** — 是否在异步上下文中阻塞（std::sync lock / 同步 IO），有无无界并发？
- **错误处理** — 错误是否被吞掉（let _ = / unwrap / expect）？错误的上下文是否完整？
- **unsafe 使用** — 是否有未经审批的 unsafe 代码块？
