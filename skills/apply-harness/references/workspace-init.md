# 一次初始化全栈工作空间

由 `apply-harness` Step 0 在多仓库模式读取。目标是一次用户调用完成协调层、前端、后端的初始化或补齐；这是当前 agent 内的执行流程，不要求新会话或多个 agent。

## 1. 发现并固定执行范围

记录协调层绝对路径。读取已有 repo-map 的仓库 id、相对路径、职责、契约与门禁配置；保留用户已有字段，只合并新发现项。每个候选路径都用 `git -C <path> rev-parse --show-toplevel` 和 `git -C <path> status --short --branch` 验证。规范化路径去重，但不能按 Git common-dir 去重而丢失不同 worktree。

扫描 `.git` 目录或文件，跳过 `.git` 内部、`node_modules`、`.venv`、`vendor`、`target`、`dist` 和技能安装目录；到达一个独立仓库后停止向下发现，已有映射或用户明确指定的嵌套仓库除外。不遍历符号链接跳出协调层；外部仓库仅在已有映射或用户明确指定时处理。

展示一张执行表：仓库 id、相对路径、角色、语言/框架、已有 Harness 状态、准备新增/补齐/沿用的内容。前后端属于不同仓库时分别检测语言，不把它们误判为“单仓多语言，需要选择焦点语言”。只询问无法判断的职责、技术栈或失效路径；已确定项继续处理。用户明确只初始化一个子仓时，缩小范围。

## 2. 初始化协调层

按主技能 Step 0.1 的补齐规则，生成以下资产：

| 目标 | 来源与边界 |
|---|---|
| `.harness/repo-map.yaml` | 按 `repo-discovery` 的格式登记真实仓库；仅执行发现与登记，不执行其需求建卡步骤 |
| `.harness/skills/common/repo-discovery/`、`workspace-orchestrator/` | 从 harness-core 的对应技能完整复制，包括支持文件 |
| `.harness/changes/README.md`、`.gitignore` | 来自 `harness-core/templates/changes/`；已有忽略文件只补 `/.runtime/` |
| `.harness/changes/_TEMPLATE/` | 只安装 workspace-change、local-change、report 模板；初始化时不创建 `WS-*` 或 `C-*` 需求 |
| `.harness/scripts/report.sh`、`review-check.sh` | 来自 core templates/scripts；无需语言参数 |

协调层不安装某个子仓的 Owner、语言规则、构建脚本或业务 hooks，不复制整个子仓 `.harness/`，也不从子仓语言参数渲染父目录。

repo-map 中的契约来源和联调命令必须来自项目实际配置；无法确定时留空并标记待配置，不能把示例命令当成已验证入口。只有真实命令确定后才生成或补齐联合门禁入口：逐仓在各自 cwd 执行本地门禁，再执行契约/联调检查，任何失败或降级均不得汇总为通过。初始化完成不代表联合门禁通过。

协调层可以暂时没有 Git；继续初始化并标注“协调资产尚未版本控制”，无需为此阻塞前后端。建立 coordinator Git 仓库或调整 submodule 拓扑不属于隐式初始化步骤；已有 coordinator 的 `.gitignore` 可补入普通嵌套仓路径，已跟踪的 submodule 除外，不执行 `git add` 或改动子仓 Git 元数据。

## 3. 逐仓初始化并返回

默认顺序处理执行表中的独立仓库。每次显式指定该仓库为 cwd，以它为目标根执行主技能 Step 0.1 和 Step 1~8；复用同一套模板，不向用户要求再次输入 `/apply-harness`。

- 每个仓库重新读取自己的包名、框架、构建工具与命令。语言参数、Owner、门禁和 hooks 的路径不能沿用上一个仓库。
- 已初始化仓库保留本地定制，补缺后验证；缺少语言包、构建环境或待决定的配置只影响该仓库，继续处理其他独立仓库。
- 子仓失败时记录具体路径、步骤和错误，清理本次创建的临时豁免标记后返回协调层；不回滚或重跑已经成功的兄弟仓库。
- 模板渲染、目录复制不是业务代码变更，不创建空 change。初始化不自动提交、发布或执行数据迁移。

## 4. 在各作用域完成技能注册

协调层和各子仓都执行主技能 Step 5.5，由 `install-skill` 统一检查注册。只扫描各根自己的 `.harness/skills/`，不要把前后端技能集中复制到父目录，也不要把整个原始 harness-core/语言包再次装进每个子仓。

分别检查“从协调层工作”和“直接打开前端/后端仓库”的技能可见性。独立 Git 子仓不保证继承协调层注册入口；某个作用域看不见同名技能时，在该作用域注册。两个互不可见的仓库各有一份技能属于正常安装，不按整个磁盘的技能名去重。

协调层通过 repo-map 和各仓库 `.harness/skills/` 的实际路径调度语言技能，无需在协调层再暴露一套前端/后端命令。原始包在项目/个人范围双重安装、同名不同版本等情况交给注册协议报告，不自动清理用户安装。

## 5. 一份结果与续跑入口

最后输出一张汇总表，每行对应协调层或一个子仓：

| 范围 | 资产 | 技能注册 | 门禁/依赖 | 后续动作 |
|---|---|---|---|---|
| 协调层 | 新建 / 补齐 / 沿用 / 待处理 | 新增 / 复用 / 冲突 / 失败 | 联调已验证 / 待配置 | 实际缺失项 |
| 前端 | 同上 | 同上 | 已验证 / 降级 / 未验证 | 实际缺失项 |
| 后端 | 同上 | 同上 | 已验证 / 降级 / 未验证 | 实际缺失项 |

用实际检查结果填表，不预填成功。全部必要资产和注册入口就绪才能称初始化完成；有冲突或失败时明确“部分完成”，但保留成功项。门禁未验证或依赖缺失单独报告，不把初始化就绪等同于可发布。

再次从协调层执行 `/apply-harness` 就是续跑入口：重新校验 repo-map 与各根文件，跳过相同内容，补齐未完成项，不依赖另建的进度数据库。仅注册失败时也可以在对应根执行 `/install-skill`；不要把它作为成功初始化后的必做步骤。

全栈初始化完成后的需求入口是 `/workspace-orchestrator start WS-001 <全栈需求>`，直接打开子仓时仍可调用本仓库的语言技能。
